# Designer autosave, recovery, and external changes

The ModernFormsNext Designer protects committed, unsaved model state with recovery snapshots and
detects changes to the two files it owns: the canonical `.mfdesign` document and its generated
`.Designer.cs` sibling. This is a recovery and conflict-avoidance feature. It is not a background
replacement for **Save**, a source-control merge engine, or a general project-directory watcher.

The persistence workflow belongs to `ModernFormsNext.Designer`. The neutral `.mfdesign` serializer
and its format-version checks remain in `ModernFormsNext.Designing`; deterministic C# generation
and conservative reverse parsing remain in `ModernFormsNext.CodeGeneration`.

## Autosave is not normal Save

Autosave writes a separate per-user recovery artifact. It never writes the canonical `.mfdesign`
file or generated C#, never advances the normal saved-revision marker, and never makes the tab
clean. A successfully protected document therefore still displays its dirty indicator and still
requires **Save** or **Save As**.

`ModernFormsDesignerOptions` exposes the focused policy surface:

- `AutoSaveEnabled` defaults to `true`;
- `AutoSaveDebounceDelay` defaults to two seconds after a committed edit;
- `AutoSaveMaximumInterval` defaults to two minutes for a continuously dirty document;
- `RecoveryRetention` defaults to 14 days;
- `MaximumRecoveryFiles` defaults to 100 retained artifacts.

Autosave is eligible only for a dirty document in a stable committed state. An active or nested
Designer transaction, rollback, normal save, load/reload, or recovery restore cannot be captured
halfway through. Transaction commit, undo, and redo notifications schedule the work through one
internal one-shot scheduler rather than through individual property events. Repeated edits reset
the quiet-period timer, while the maximum interval remains an upper bound.

Each open document has independent scheduling, revision, writer, watcher, and conflict state. Only
one recovery write can run for a document at a time. The snapshot records the committed revision
and its revision generation before background I/O begins. If the document advances while that
write is running, completion of the older write does not claim the newer state; another snapshot
is scheduled. Autosave neither adds nor removes undo/redo entries.

Normal Save first serializes the model and, when `AutoGenerateDesignerCodeOnSave` is enabled,
prepares generated code before replacing destinations through same-directory temporary files.
Each replacement is flushed and atomic at its own file boundary, so a failure before replacement
leaves that destination intact. The two files are not a filesystem transaction: if either attempted
write fails, the Designer keeps the document dirty, retains recovery, does not advance the saved
marker, and reports the failure. Recovery is deleted only after the normal save has completed
successfully.

## Recovery location and document identity

The default recovery root on Windows is:

```text
%LOCALAPPDATA%\ModernFormsNext\Designer\Recovery
```

If the operating system does not provide a local-application-data directory, the Designer uses the
same `ModernFormsNext\Designer\Recovery` subtree below the system temporary directory. Recovery is
not written beside a project file.

A saved document identity hashes both its canonical `.mfdesign` path and optional canonical
project path. It therefore does not rely on a filename such as `Form1.mfdesign`, which could occur
in many projects. A new document without a path receives a session-stable temporary GUID, a
suggested name, and the available project context. It remains recoverable but still requires
**Save As** before it can become a canonical project document.

Artifact names also contain a Designer session ID and process ID. Two Designer or Visual Studio
processes do not blindly replace one another's recovery artifact. This is not distributed locking:
their canonical writes are instead detected as external changes by the other process.

## Versioned recovery envelope

Recovery format version 1 is an envelope around ordinary, deterministic `.mfdesign` JSON. Its
version is independent from the version of the embedded design document.

| Field group | Purpose |
| --- | --- |
| Format and framework version | Rejects unsupported recovery envelopes and identifies the writer. |
| Document identity | Distinguishes saved-path/project identities from temporary unsaved IDs. |
| Document and project paths | Provides display and comparison context; it is not authority to overwrite that path. |
| Suggested name and timestamp | Identifies an unsaved document and the age of the snapshot. |
| Source timestamp and SHA-256 hashes | Compares the snapshot with the canonical `.mfdesign` and generated C# states. |
| Dirty revision and revision generation | Prevents stale background completion from claiming a newer edit. |
| Session and process IDs | Keeps simultaneous Designer sessions separate. |
| Serialized design document and SHA-256 checksum | Carries data-only model state and detects partial or corrupt payloads. |

The envelope does not persist `DesignerSession`, live controls, native handles, delegates,
clipboard contents, undo/redo units, selections, dispatcher objects, or Skia resources. Recovery
deserialization validates bounded input, document depth and node count, model invariants, and the
payload checksum. It does not resolve project assemblies, invoke custom control constructors, or
execute project code. Project UserControls retain the same data-only preview boundary as an
ordinary `.mfdesign` load.

Recovery and canonical writes use this sequence:

```text
serialize completely
    -> create unique temporary file in the destination directory
    -> write UTF-8 and flush to durable storage
    -> atomically replace an existing file or move into a new destination
    -> remove the temporary file after a failed or successful handoff when possible
```

A failed write before the final handoff cannot truncate the previous valid artifact. A malformed
checksum or invalid document is classified as corrupt instead of being loaded. An unknown recovery
envelope version is reported as unsupported. Such artifacts do not crash startup and can be moved
to the dedicated `Quarantine` subtree for diagnosis and bounded cleanup.

### `.mfdesign` format compatibility

Issue #41 does not bump the canonical design-document format: the current
`metadata.formatVersion` remains 1, and every new save writes that version explicitly. A legacy
document with no declared format version is read as version 1 for backward compatibility and the
diagnostic load API reports that assumption. A declared future version is rejected with an error
at `$.metadata.formatVersion` instead of being partially loaded.

`DesignDocumentSerializer` also accepts an explicit set of trusted `IDesignDocumentMigration`
steps. Each step transforms JSON from one declared older version toward the current version and can
return user-facing diagnostics. The serializer validates a strictly advancing chain and the
declared output version at every step before materializing a `DesignDocument`. There is currently
no built-in catalog for arbitrary historical or third-party versions: a declared older version
without a registered migration is rejected clearly. Migration is data-only and must not load a
project assembly or execute user code.

## Discovery and recovery choices

Startup/open discovery enumerates only the dedicated recovery root, with bounded entry, candidate,
per-artifact, and aggregate-byte limits. Production defaults inspect at most 4,096 top-level
entries, retain the 512 newest candidate paths for inspection, read at most 32 MiB per artifact,
and read at most 128 MiB across one discovery pass. It does not search projects, repositories,
user-profile folders, or the whole disk. Candidates are validated before they are offered.

For a saved document, the Designer compares the current canonical hash with both the source hash
captured by autosave and the recovered payload:

- a payload already identical to the canonical file is obsolete and is not offered;
- a changed recovery payload whose canonical source still matches its captured source is
  recoverable;
- a canonical file that differs from both states is a recovery conflict and neither side is
  selected automatically;
- a missing canonical file keeps the in-memory/recovery copy available for **Save As**.

For an unsaved document there is no canonical hash. Its temporary identity and valid payload are
sufficient to offer recovery.

The nonmodal safety banner identifies the document and whether recovery is available or conflicts
with disk. The notification retains recovery/disk timestamps for its comparison details. Its core
choices are:

- **Restore** loads the data-only snapshot into the Designer;
- **Keep** dismisses the current banner without deleting the artifact;
- **Open Disk** leaves a conflicting recovery artifact intact while opening the canonical
  file;
- **Save As** gives a conflicting or previously unsaved snapshot a new destination;
- **Compare** shows trusted recovery/disk timestamps and SHA-256 fingerprints;
- **Discard** explicitly deletes the recovery artifact.

A restored document starts with empty undo/redo history but remains dirty relative to disk. There
is no synthetic “undo crash recovery” operation and no persisted pre-crash history. Normal Save or
Save As is still required. Recovery already matched to an open canonical document can retain that
host-approved path. A startup candidate restored before its canonical document is attached opens as
an unsaved copy and requires Save As; the metadata path is never adopted silently. Closing with
**Don't Save** deletes that document's recovery state; canceling close leaves both the document and
its scheduling active.

An attached recovery banner is a required decision point. Until the user chooses an action, the
Designer blocks same-path Save and generated-code replacement so the pre-crash version cannot be
deleted accidentally. Saving the current disk version elsewhere leaves the recovery candidate
available as a separate choice. If the user edits the current document before choosing **Restore**
or **Open Disk**, the Designer first forces a recovery snapshot of those new edits before replacing
the in-memory baseline.

## External `.mfdesign` changes

Each saved document watches only its containing directory and filters notifications to the exact
`.mfdesign` path and exact generated-code sibling. Native filesystem events are hints: duplicate
Changed notifications, create/replace sequences, and rapid writes are coalesced, then final content
is verified by SHA-256. A native watcher-buffer error requests a fresh check of both exact targets.
Timestamps are diagnostic/prefilter data, not the final equality test.

Expected post-write hashes suppress notifications caused by the Designer's own Save. Suppression
is content-based, not a time window, so a second Visual Studio instance that writes different
content is still detected. Notifications received during an active transaction or persistence
operation are deferred until the model is stable. Normal Save and explicit code generation also
re-fingerprint both canonical targets synchronously immediately before writing. This preflight
prevents a delayed or lost watcher event from allowing an external edit to be overwritten.

Behavior depends on dirty state:

- **Clean document:** a valid external `.mfdesign` change is reloaded as a new clean baseline.
  Undo/redo history is cleared, and selection is retained by node name when that node still exists.
- **Dirty document:** the Designer does not reload automatically. A nonmodal conflict banner offers
  **Keep Designer Version**, **Reload Disk Version**, and **Save Designer Version As**. Keeping the
  Designer version acknowledges the observed disk hash and leaves the model dirty. Reloading is an
  explicit destructive choice and first preserves the current recoverable state.
- **Deleted or renamed away:** the in-memory document remains available and its dirty state is
  retained. The Designer reports the missing file and allows Save or Save As. Without an explicit
  host/project-system rename event, the watcher treats a rename as deletion plus an unrelated new
  file; it does not guess identity from the filename.
- **Invalid or partially written file:** parsing failure leaves the current document, history, and
  selection unchanged and reports a diagnostic.

**Compare** is intentionally a read-only fingerprint summary, not a text diff or merge editor. A
recovery comparison also includes recovery/disk timestamps; a live external-change comparison
reports the known Designer and current disk hashes. This helps confirm that content differs without
rendering or executing it. Use source control or an external diff tool before choosing Keep,
Reload, or Save As when a line-level comparison is required.

## External generated-code changes

The generated `.Designer.cs` sibling is watched because it can be edited by another process. The
Designer waits for stable content and runs only the conservative ModernFormsNext reverse parser;
arbitrary C# is never executed.

- A clean active Designer document accepts a successfully parsed external generated file as one
  transactional document replacement. The imported model is dirty because `.mfdesign` has not yet
  been saved. A clean inactive tab waits for activation and explicit Reload instead of switching
  session ownership behind the user's back.
- A dirty Designer document is never silently replaced by generated code. It enters the same
  explicit conflict workflow.
- Unsupported or partial C# produces parser diagnostics and leaves the current model unchanged.
- If both files change in one coalesced interval, `.mfdesign` takes precedence as the canonical
  source. The Designer does not merge two representations automatically.

Reverse parsing continues to support only the deterministic subset emitted by
`ModernFormsNext.CodeGeneration`. Improving arbitrary-source fidelity remains separate work; see
[#81](https://github.com/ProGraMajster/ModernFormsNext/issues/81).

## Cleanup, diagnostics, and failures

Successful normal save and explicit **Don't Save** remove obsolete recovery for the affected
document. Startup/maintenance cleanup is restricted to owned `.mfrecovery`, recovery temporary,
and quarantined files below the dedicated root. Age and count limits are applied without following
reparse points outside that root, and recovery for a currently open dirty document is protected.

Disk-full, access-denied, sharing, unavailable-path, checksum, parsing, and watcher failures do not
make a dirty document clean. The existing recovery artifact is retained where possible. The
Designer status/output surfaces report autosave success or failure, the protected revision and
artifact identity, pending work, and external conflict or missing-file state. “Recovery copy
saved” never means “document saved.” Hosts and support tooling can use
`ModernFormsDesignerShell.CheckForExternalChanges()` for an immediate hash-based recheck and
`RecoveryDirectoryPath` to report the owned recovery location.

The shell's tab close button runs the Save/Don't Save/Cancel workflow. A hosting window must call
`ModernFormsDesignerShell.ConfirmCloseAsync(owner)` from its closing flow before it disposes the
shell; this gives every dirty tab the same decision and ensures an explicit Don't Save removes its
artifact. The standalone Designer Playground and out-of-process Visual Studio Designer host both
use this guarded close flow. `SaveDocument(path)` is the host-facing explicit-path save used when an IDE has already
chosen the destination. A project system that knows a moved item's identity should call
`NotifyDocumentRenamed(path)`; raw watcher renames intentionally remain delete-plus-create. A host
that already received its own explicit Don't Save decision can call
`DiscardActiveDocumentRecovery()`, but must not do so for a crash or canceled close. Before treating
a clean model as disposable, an IDE host can inspect `HasUnresolvedRecovery`; the Visual Studio pane
uses it to preserve an attached pre-crash copy when `Close()` provides no explicit discard reason.

## Privacy and security

Recovery is a local resilience cache, not a secret store. An artifact contains the full serialized
design model and metadata may contain absolute document and project paths. It is not encrypted.
Operating-system user-profile permissions are the primary access boundary; do not redirect the
recovery root to a shared or synchronized location when documents contain sensitive information.
SHA-256 detects accidental truncation or corruption but does not authenticate an artifact against
another process running as the same user.

Paths read from recovery metadata are display/comparison context only. Restore does not silently
write to them. Save As requires an explicit destination, and deletion/quarantine/cleanup first
prove that the target is an owned file below the normalized recovery root. Directory reparse points
are rejected so cleanup cannot escape through a junction or symbolic link.

## Current boundaries

- The interactive Designer and its file watcher are Windows-first; builds and headless tests do not
  constitute an observed Visual Studio or filesystem smoke test.
- Recovery persists the design model, not undo/redo history, selection, clipboard state, or project
  executable state.
- There is no distributed lock, three-way merge, recovery index database, line-level comparison
  view, or automatic identity inference after an external move. The built-in Compare action shows
  recovery timestamps and content hashes only.
- External tracking is limited to the exact `.mfdesign` and generated `.Designer.cs` files. Project
  resources and arbitrary dependencies are outside this feature.
- Reverse import remains constrained to generated-code syntax the conservative parser recognizes.
- Atomic replacement protects each file independently; it cannot make `.mfdesign` and
  `.Designer.cs` one cross-file transaction or compensate for storage that violates rename/flush
  guarantees.

## Manual Windows validation checklist

Automated tests cover scheduling, revision races, serialization integrity, bounded discovery,
cleanup containment, synthetic watcher bursts, and model/history behavior. The following remains
an interactive gate and must be reported as observed or pending rather than inferred from tests:

1. In the Designer Playground or a Visual Studio Experimental Instance, edit a saved document and
   verify that the tab stays dirty, the canonical `.mfdesign` hash is unchanged, and a recovery
   artifact appears after the debounce interval.
2. Save normally and verify that `.mfdesign` and `.Designer.cs` contain the committed model, the tab
   becomes clean, and obsolete recovery is removed.
3. Edit again, terminate the Designer process without closing documents, reopen it, and verify that
   the recovery banner identifies the document and Compare reports its timestamp/fingerprint.
   Restore it and verify that the model is correct, history starts empty, and the tab remains dirty
   until Save.
4. Repeat recovery for a new document without a path, then use Save As and verify that the chosen
   `.mfdesign` and generated-code sibling are created without reusing another document's path.
5. With a clean tab open, replace its `.mfdesign` externally and verify one stable reload, clean
   history, and retained selection when the selected node still exists.
6. Repeat with local dirty edits and verify a nonmodal conflict instead of automatic reload. Exercise
   Keep Designer Version, Reload Disk Version, and Save Designer Version As on separate copies.
7. Delete and rename the watched `.mfdesign`; verify a missing-file status, an intact in-memory
   model, and a working Save As path.
8. Modify `.Designer.cs` with valid generated-shape C# and then with unsupported/partial C#. Verify a
   single transactional import for valid stable content and no model mutation on parser failure.
9. Save from the Designer and verify that its own watcher produces no conflict. Then write different
   content from a second process/Visual Studio instance and verify that the change is detected.
10. Corrupt a copied recovery artifact and verify a clear invalid/unsupported diagnostic, no startup
    crash, no model load, and quarantine or safe discard limited to the recovery root.
11. Exercise rapid edits, a long drag/collection transaction, rapid external replace events, and
    closing during pending autosave. Verify no partial snapshot, duplicate prompt, stale clean marker,
    or post-disposal callback.
12. Repeat with multiple saved and unsaved tabs. Verify independent artifacts/conflicts and no
    recovery prompt for a document that was saved or explicitly closed with Don't Save.

Record the host, Windows and Visual Studio versions, commit SHA, and observed result for every
interactive run. See [Designer transactions and undo/redo](designer-transactions-and-undo.md) for
the saved-revision and transaction contract, and [Designer architecture](designer-architecture.md)
for project boundaries.
