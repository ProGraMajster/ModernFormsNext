# Migrate from ModernFormsNext 1.11.1 to 1.12.0

The template and ordinary Form startup remain code-first on .NET 10.
Upgrade references together, rebuild the application, and test the workflows
below where they apply. Package commands for 1.12.0 require the coordinated
release assets or a validated local feed. Use the [release notes](../1.12.0-release-notes.md)
and [changelog](../../CHANGELOG.md) for feature and verification detail.

## Packages and tools

- Update every directly referenced ModernFormsNext package to `1.12.0`,
  including packages in `Directory.Packages.props` if you use central
  package management. Keep optional automation, testing and notification
  packages aligned with the runtime and backend.
- Windows applications continue to target `net10.0-windows`. Use .NET 10;
  the repository pins SDK 10.0.401, and the Android build uses workload set
  10.0.401.1 (Android 36.1.69), JDK 21 and API 36 build inputs.
- `AssemblyVersion` advances from `1.11.0.0` to `1.12.0.0` for the minor
  line. Rebuild consumers together. Review explicit assembly identities,
  custom loading rules or binary plugins if your deployment uses them.
- Update the project template with
  `dotnet new install ModernFormsNext.Templates::1.12.0` when available.
  This changes future projects. Existing project files and source still
  belong to the application and should be upgraded in place. Compare a
  temporary generated application if you maintain your own startup.
- Install the matching 1.12.0 VSIX for Designer use. A .NET 10 project
  should use a Visual Studio version that supports .NET 10 SDK projects.
  The amd64 VSIX manifest's Visual Studio 2022 install range and its
  separate .NET 10 host runtime do not qualify VS 2022 as a .NET 10
  project toolchain. See the
  [compatibility matrix](../visual-studio-designer-host.md#visual-studio-and-net-compatibility).

```powershell
dotnet add package ModernFormsNext --version 1.12.0
dotnet new install ModernFormsNext.Templates::1.12.0
dotnet new mfn-app -n MigrationScratch
```

## Runtime behaviors to review

Ordinary starter application code keeps the same startup shape. No new
application initialization step is required for the Windows template.
The following corrections may affect applications that relied on previous
geometry or event behavior.

| Area | Check during migration |
| --- | --- |
| Scroll | Review custom handlers for assumptions that Scroll only represents pointer interaction. Consume the reported orientation and committed old/new values. `ScrollControlIntoView` can reveal a descendant in nested viewports. |
| Parent changes | Remove any dependency on duplicate `ParentChanged` calls after setting Parent. Check handlers used by both direct parenting and collection operations. |
| Form size constraints | Changing one bound can coerce the other. Both changed constraints now notify. Keep handlers tolerant of a consistent paired value. |
| Focus and validation | Exercise cancelled validation, closing dialogs, focus handoff and custom activation. Use the standard transition and event paths in preference to app-owned duplicate focus state. |
| Typography and layout | TabControl headers and NumericUpDown editors now use the effective owner typography. Check autosized labels, ellipsis, mixed DPI and right-to-left Flow/Table layouts with actual fonts and localized strings. |
| ToolTip | Check inactive-window behavior, `ShowAlways`, animation/fading flags and custom painting. Owner-draw code retains its Draw handler; use the documented presentation lifecycle when sharing tooltip state. |
| ListView | Existing consumers retain eager realization by default. To opt in to virtualization, set `VirtualizationEnabled` and configure `ItemSize` or `ItemsLayout`. Recheck selection, focus, keyboard reveal, and custom item presentation. |
| Windows chrome | Check native Snap, maximize, restore and taskbar access for forms with custom chrome. Keep managed and system decorations configured through the Form. |

New controls cover [collections](../collection-view.md),
[paged collections and refresh](../collection-utilities.md),
[search and time](../search-and-time.md) and [record navigation](../binding-navigator.md).
The [control catalog](../controls/README.md) includes individual examples.
New [page navigation](../pages-and-navigation.md) and [AppShell routing](../app-shell-routing.md)
are optional. They do not require migrating existing forms to pages.

## Existing Designer documents

Keep the `.mfdesign` document, user code and generated `.Designer.cs` file
together. Open an existing document with **View ModernFormsNext Designer**
and make a small, reversible edit before regenerating your project. Inspect
the resulting C# diff. The supported static subset can round-trip; the
Designer reports unsupported source edits or conflicts through the
[reverse-sync workflow](../designer-architecture.md#current-designer-limitations).
Keep handwritten code in the user-authored partial class.

Older generated `ClientSize` syntax remains accepted by reverse parsing;
newer generation uses the documented Form size convention. 1.12.0 can
add page slots, metadata for inherited designs, and supported geometry or
animation definitions when those features are authored. Avoid manually
copying new metadata into a project that still uses an older editor.
The standard 1.12.0 VSIX uses the data preview and placeholders for
unavailable custom controls. Existing user code can continue to execute at
application runtime.

## Android projects

When taking the new experimental Android package, reference
`ModernFormsNext.WindowKit.Backend.Android` at exactly `1.12.0`. It was
absent from 1.11.1. Use the Android workload, the documented minimum API 23,
and the explicit Activity/shared surface or bounded `AndroidWindowActivity`
host. Review [permissions](../android-permissions.md),
[host lifecycle](../android-windowing.md) and
[package setup](../android-backend.md#nuget-package-experimental).
Distinguish the deterministic `net10.0` asset from the native Android asset.

Android remains experimental. Qualify your declared device/API/IME matrix,
saved-state contract and accessibility behavior separately. The
[release matrix](../android-release-validation.md) records the observed
device, 60 Hz and coverage limits. Older .NET targeting and executable
Designer preview are tracked for 2.0.0.
